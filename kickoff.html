Start with one Java simulator application. Simple settings describe names, durations and supported connections. Java code implements new behaviour through documented extension points. The two reference models guide the abstractions. New machine types may need new code; the aim is to keep such changes local and document any necessary core changes.

Initial timing: a configured three-second action completes after approximately three real seconds.

One shared scheduling component handles delayed actions. Preserve the current HTTP response timing and MQTT behaviour during migration. Tests can control pending actions through a scheduler test helper. Accelerated simulation time is deferred. This is ordinary real-time pacing with timing tolerances, not a hard real-time guarantee. Interface compatibility remains a requirement to verify.

Keep workpiece state consistent. Unit tests check controlled event order; integration tests allow agreed timing tolerances. Exact live timestamps do not need to match across runs.
