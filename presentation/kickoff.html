Project proposal and implementation plan

About 10–12 minutes plus discussion. The project is currently at the design stage. This deck proposes a Java implementation during the IMP and needs agreement on scope with the professor and advisor.

Motivation

Testing with physical systems

Hardware access can limit when and how we test an application.

Limited availability

Devices and installations may be shared, expensive, or unavailable during development.

Difficult failure tests

Outages, delays, and recovery can be disruptive to reproduce on real equipment.

A simulator lets us run controlled scenarios and repeat them after software changes.

The motivation is access to a controllable test environment. Avoid claiming that a simulator can fully validate physical behavior. Its usefulness depends on how well the modeled behavior matches the application’s needs.

Project overview

One engine, different system models

Build a Java simulator whose core stays the same when the modeled system changes.

01

Generic engine

Runs time, events, and state changes.

02

System definition

Provides components, connections, and behavior for each use case.

03

Application interface

Carries commands and telemetry between the application and simulator.

The central question is whether two meaningfully different use cases can run without changing the engine. Configuration describes the system structure. Java behavior code supplies the rules for individual component types. There is no runnable implementation yet.

The use case defines what happens. The engine runs it. The adapter exposes the interface the application expects.

Keep this discussion coarse grained. A factory or lab definition configures the same engine. The application sends commands leftward and receives telemetry rightward. Protocol choice and how live commands map to simulation time remain open. Interface compatibility is a design goal, not a demonstrated result.

Initial requirements

What the first version should support

01Define a system

Components, initial state, and typed connections.

02Run timed behavior

Process events in a defined order and update state.

03Exercise failures

Schedule delays, outages, and recovery.

04Connect an application

Accept commands and publish telemetry through one adapter.

05Repeat and reuse

Repeat runs with fixed inputs and support two use cases on the same core.

These are initial requirements to refine with the advisor. Repeatability requires defined ordering and controlled randomness. For live inputs, capture or replay commands if comparing runs. Limit the first implementation to one communication adapter.

Implementation scope

Two small use cases

First model

Factory process

Two machines and a conveyor.

Processing time, transfer delays, machine failure, and recovery.

Reuse check

IoT lab

Sensors and a controller.

Periodic readings, communication delays, device outage, and recovery.

The second model should need new definitions and behavior, with no changes to the core.

Outside the planned scope: detailed physics, 3D visualization, distributed simulation, and production-scale performance.

These are candidate demonstrations, not confirmed case studies. Choose minimal models that exercise different behavior: process flow versus periodic measurements and commands. The proposed IMP scope extends the current design-only documentation into an implementation. Confirm that expectation at kickoff. Avoid making a dashboard a separate major work package.
